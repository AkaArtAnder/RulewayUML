# Условие — материалы прототипа

Статус: прототип принят владельцем 2026-09-22 и оформлен публичным компонентом. Для применения используйте [спецификацию условия](../../specification/components/condition.md), [condition.puml](../../../components/condition.puml) и примеры из `examples/`. Ниже сохранены материалы обсуждения и история проверок прототипа; они не подтверждают проверку публичной версии. Основание — [задача прототипа](../../tasks/2026_09_22_condition_prototype.md).

## Предложение

Условие содержит два обязательных значения:

| Значение | Для чего | Пример |
| --- | --- | --- |
| `$question` | Вопрос, на который можно однозначно ответить по указанному основанию | «В заключении есть замечания?» |
| `$basis` | Результат действия, документ или правило, по которому выбирается ответ | «РСЗ-02: заключение» |

Ответственный, срок и работа по проверке остаются в предшествующем действии. Условие отображает выбор пути по полученному результату. Новый формат идентификаторов условий не вводится: код в основании ссылается на существующее действие.

Для прототипа выбрана **функция**, возвращающая подпись, а не процедура, открывающая ветвление. Благодаря этому одна форма `$ruleway_condition($question, $basis)` используется внутри стандартного `if` и `repeat while`. Возможность возвращать текст в описание диаграммы предусмотрена [препроцессором PlantUML](https://plantuml.com/preprocessing). Историческое определение сохранено в [condition_prototype.iuml](condition_prototype.iuml); его дальнейшая разработка ведётся в [публичном компоненте](../../../components/condition.puml).

```plantuml
if ($ruleway_condition("Заявка согласована?", "РСЗ-01: решение по заявке")) then (да)
  $ruleway_action("РСЗ-02", "Сообщить о согласовании", "Согласующий", "Инициатор получил подтверждение согласования")
else (нет)
  $ruleway_action("РСЗ-03", "Сообщить об отказе", "Согласующий", "Инициатор получил отказ с указанием причины")
endif
```

Предшествующее действие `РСЗ-01` и полная схема находятся в [decision.puml](decision.puml).

## Предлагаемые правила заполнения

1. Задавать конкретный вопрос по результату проверки или принятому решению. Вместо «Всё хорошо?» — «В заключении есть замечания?».
2. Указывать основание, доступное к моменту выбора пути. Условие само не выполняет проверку и не принимает решение за ответственного.
3. Подписывать оба исхода бинарного вопроса: `да` и `нет`. Путь при отсутствии данных нужно определить отдельно, если он возможен в процессе; отсутствие ответа не равно ответу «нет».
4. Показывать дальнейшие действия стандартными конструкциями. Все действия оформлять через `$ruleway_action`.
5. Для замечаний показывать доработку и повторную проверку. Окончательный отказ — отдельный предметный исход. Ограничения повторов задавать только при наличии соответствующего правила, вместе с дальнейшим исходом.
6. Держать вопрос и основание краткими. Ручные переносы внутри значений задавать через `%newline()`.

Весь текст использует DejaVu Sans, размер 14, как в компоненте действия. Вопрос отображается жирным и центрируется относительно блока, включая каждую строку многострочного вопроса. После него оставляется пустая строка, затем у левого края выводится основание: подпись **«Основание:»** — жирная, значение — обычное, по аналогии с параметрами действия. Дополнительные пустые строки перед вопросом и после основания обеспечивают внутренние отступы от верхней и нижней границ блока. Для многострочного текста каждый фрагмент оформляется отдельно, чтобы теги не появлялись в подписи.

Прототип использует общий стиль библиотеки и локально задаёт для `diamond` параметры `FontName DejaVu Sans`, `FontSize 14` и `HorizontalAlignment center`. Маркер `<center>` перед строками вопроса и `<left>` перед строками основания обеспечивает разное выравнивание разделов. Общий `components/style.puml` не менялся; это экспериментальная настройка в `condition_prototype.iuml`.

## Примеры

- [Два окончательных исхода](decision.puml): действие фиксирует согласование или отказ; условие направляет к соответствующему уведомлению. Это отдельный учебный сценарий, допускающий отказ; такого правила в основной пример не добавлено.
- [Доработка](rework.puml): замечания возвращают к подготовке заявки и повторной проверке. При отсутствии замечаний заявка передаётся на согласование. Показан фрагмент подготовки, а не весь процесс принятия решения. Лимит повторов не задан.
- [Длинный критерий](long_condition.puml): два ряда вопроса и основания в цикле проверки комплекта документов. Это проверка читаемости переносов.

Условие в цикле записывается той же функцией:

```plantuml
repeat while ($ruleway_condition("В заключении есть замечания?", "РСЗ-02: заключение")) is (да) not (нет)
```

## Проверки и ограничения

По просьбе владельца после унификации шрифта рендеринг, проверки и самостоятельное ревью не выполнялись. Ниже зафиксированы результаты предыдущих итераций.

- На PlantUML `1.2026.5` в Docker пройдены синтаксис и экспорт всех трёх схем в SVG/PNG. Сеть отключена, пользователь `vscode`, исходники только для чтения.
- Все три PNG просмотрены: кириллица, знак, подписи исходов и направление возврата читаются; исправлено отображение тегов при многострочном вопросе и основании.
- После замечаний по оформлению все три схемы повторно проверены в SVG/PNG: подпись «Основание:» жирная, значение обычное, между вопросом и основанием есть пустая строка. PNG просмотрены; начертание и отступ дополнительно подтверждены по SVG.
- После добавления внутренних отступов сверху и снизу синтаксис и SVG/PNG всех трёх схем повторно проверены в Docker. PNG просмотрены: текст отделён от границ, длинные подписи и переходы читаются.
- После центрирования вопроса все три схемы снова проверены в SVG/PNG, PNG просмотрены. По координатам SVG подтверждены центрирование каждой строки вопроса относительно блока, левое выравнивание основания и сохранение внутренних отступов. Маркеры выравнивания не отображаются в тексте.
- Пустой вопрос и пустое основание отклоняются с соответствующей ошибкой `Ruleway`, код `200`.
- Функция проверяет только непустые строки. Пробелы вместо текста, смысл вопроса, существование указанного действия, полнота исходов и правильность переходов автоматически не проверяются. Подписи `да`/`нет` — правило автора; функция не может запретить пропуск `else` или подписи ветви.
- Поддержка многовариантного выбора, автоматическая проверка маршрутов и новая публичная процедура не заявляются. Прототип не вычисляет ответы и не исполняет процесс.
- SVG созданы; отдельный визуальный просмотр SVG в браузере не выполнялся. Новых гиперссылок в диаграммах нет, проверка навигации не требуется.

## Воспроизведение

Из корня репозитория с существующим Docker-образом:

```bash
docker run --name ruleway-condition-preview --network none --user vscode \
  --mount "type=bind,source=$PWD,target=/workspace,readonly" \
  --workdir /workspace rulewayuml-dev:plantuml-1.2026.5 bash -lc '
    set -e
    plantuml -charset UTF-8 -checkonly docs/design/condition_component/*.puml
    for format in svg png; do
      plantuml -charset UTF-8 -failfast2 -t"$format" \
        -o /tmp/ruleway-condition-preview docs/design/condition_component/*.puml
    done
  '
mkdir -p /tmp/ruleway-condition-preview
docker cp ruleway-condition-preview:/tmp/ruleway-condition-preview/. /tmp/ruleway-condition-preview/
docker rm ruleway-condition-preview
```

Результаты до унификации шрифта, с центрированным вопросом и внутренними отступами, сохранены вне исходников в `/home/rtndr/.codex/visualizations/2026/09/22/01a0c878-4e89-7e33-84ac-2e76ef0b8f6c/condition_component/centered/`. Новые изображения после изменения шрифта не создавались. Предыдущие варианты находятся в соседних каталогах `vertical_padding/` и `label_spacing/`, первоначальные изображения — в родительском каталоге.
