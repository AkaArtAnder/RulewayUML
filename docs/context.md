# Контекст проекта RulewayUML

Актуализировано: 2026-09-19. Стадия: реализован общий стиль регламентов; предметные компоненты библиотеки формируются.

## Назначение и принятое решение

**RulewayUML — база переиспользуемых UML-компонентов для построения регламентов на языке PlantUML.** Регламент представляется наглядной схемой с действиями, ролями, артефактами и условиями переходов. Основой служат диаграммы деятельности (activity diagrams).

По сообщению владельца проекта от 2026-09-17, по итогам продуктовой аналитики принято решение не разрабатывать самостоятельное приложение, а создать библиотеку компонентов PlantUML. Это действующее продуктовое решение. Первоначальная идея приложения объясняет предметную область, но не является заданием на реализацию всех его функций.

Под «компонентом» здесь понимается переиспользуемый элемент описания регламента, а не обязательное использование UML-диаграммы компонентов. Ruleway — имя в фирменных материалах; RulewayUML — имя проекта и репозитория.

## Исходная проблема

В заметке выделены две проблемы:

- **Регламент трудно понять.** Большой текстовый документ скрывает последовательность действий, связи между процессами, необходимые документы и распределение ролей. Нужна схема, которая объясняет назначение процесса и порядок работы, связывая необходимые материалы в одном представлении.
- **Регламент отделён от реальной работы.** Исполнителю приходится помнить порядок действий, искать нужные документы и сверять решения с текстом. Первоначальная идея предполагала интерактивную среду, которая ведёт сотрудника по процессу и собирает результаты его работы.

Библиотека направлена прежде всего на первую проблему. Во второй она помогает явно описать действия, результаты и контрольные точки, но сама не запускает процессы, не отслеживает их состояние и не обеспечивает соблюдение регламента.

## Пользователи и сценарии

Это рабочие предположения, выведенные из исходной идеи; отдельное исследование аудитории не предоставлено.

| Пользователь | Задача | Ожидаемая польза |
| --- | --- | --- |
| Автор регламента: аналитик, методолог, владелец процесса | Описать процесс с помощью готовых компонентов | Меньше ручного оформления, единый способ описания |
| Исполнитель процесса | Прочитать схему и найти материалы нужного шага | Понятны ответственность, входы, результат и дальнейшие действия |
| Проверяющий или согласующий | Проверить полноту и непротиворечивость регламента | Видны пропуски ролей, результатов, условий и контрольных точек |

Целевой сценарий: автор описывает регламент текстом PlantUML, подключает компоненты библиотеки, получает диаграмму и размещает её вместе с инструкциями и артефактами в выбранной системе документации. Исполнитель использует схему как навигацию по процессу. Совместимость с конкретной системой публикации пока не определена.

## Предметная модель

Исходная заметка требует отражать в регламенте следующий состав. Это требования к выразительности будущей библиотеки, а не список уже реализованных компонентов или обязательных параметров каждого блока.

| Понятие | Что необходимо выразить |
| --- | --- |
| Регламент и границы процесса | Назначение, событие начала, условия завершения и ожидаемый результат |
| Роль | Кто отвечает за действие или участвует в нём; роль не равна учётной записи |
| Шаг | Конкретное действие в последовательности работ |
| Вход и выход | Необходимые исходные данные и ожидаемые результаты шага или процесса |
| Артефакт | Документ, шаблон, запись или иной материал, связанный с действием |
| Переход и условие | Порядок действий, ветвление, повторение или параллельная работа |
| SLA / срок | Описанное ограничение по времени или уровню обслуживания; без автоматического отсчёта |
| Контроль и метрика | Условие проверки результата и определение показателя; без автоматического сбора |
| Исключение | Нестандартная ситуация и предусмотренный путь её обработки |
| Инструкция и чек-лист | Пояснение к действию, перечень проверок или ссылка на подробный материал |
| Подрегламент | Самостоятельный дочерний процесс с кратким описанием, входами, выходами и переходом к деталям |
| Группа шагов | Визуальное объединение внутри текущей схемы без выделения отдельного регламента |
| Термин | Согласованное определение для пояснения текста схемы |

Ключевое различие: библиотека описывает **правила выполнения процесса**, а экземпляр процесса, фактический исполнитель, выполненный чек-лист и собранные результаты относятся к среде исполнения за пределами текущего продукта.

## Как исходные требования переходят в библиотеку

Таблица фиксирует адаптацию требований к принятому формату. Конкретные конструкции PlantUML и полнота первой версии ещё требуют прототипирования.

| Первоначальное требование из AFFiNE | Трактовка для RulewayUML |
| --- | --- |
| Полный состав регламента: границы, роли, входы/выходы, шаги, SLA, контроль, метрики, исключения, инструкции, чек-листы, артефакты | Сохранить как ориентир предметной модели; распределить по компонентам и примерам |
| Иерархия регламентов с переходом к дочернему | Представлять дочерний регламент кратким блоком с входами, выходами и ссылкой на детали; работоспособность навигации проверять в выбранном формате публикации |
| Activity-диаграммы с адаптированными блоками | Использовать диаграммы деятельности как основу представления |
| Артефакты, чек-листы, инструкции, ссылки и ответственные внутри блоков | Проработать читаемые шаблоны шагов и связанных пояснений; не перегружать схему полным текстом документов |
| Агрегирующие блоки без создания подрегламента | Поддержать визуальные группы шагов в одной диаграмме |
| Настройка цветов, контуров, иконок и компоновки через контекстное окно | Настройки оформления задавать текстом; контекстное окно и визуальный редактор исключены. Гибкость компоновки и иконок проверить на прототипах |
| Пользовательские роли и ролевой доступ | Показывать роли процесса; аутентификация и права доступа находятся вне библиотеки |
| Перенос регламента в Markdown при миграции | Хранить описание в текстовом исходнике PlantUML, предусмотреть примеры его использования в Markdown. Автоматическое преобразование всего регламента в Markdown не принято в объём работ |
| Главный экран: создание, редактирование, просмотр, запуск, текущие и завершённые процессы, статистика и артефакты | Не реализовывать интерфейс приложения, запуск процессов, историю исполнения и статистику |
| Общий источник терминов с подсказками в интерфейсе | Рассмотреть общие определения, легенду и ссылки в документации; интерактивный словарь не обещан |

## Границы проекта

В текущем направлении работ: компоненты PlantUML, соглашения по описанию регламентов, оформление, документация, примеры и проверки их рендеринга.

За пределами проекта: самостоятельное веб- или desktop-приложение, графический редактор, сервер и база данных исполнения, учётные записи и разграничение доступа, назначение реальных задач, уведомления, контроль сроков в реальном времени, сбор фактических метрик и хранение артефактов выполнения. Потребность в этих функциях требует отдельного продуктового решения.

После успешной сборки внутри контейнера окружение можно проверить командами `plantuml -version` и `plantuml -help`. Это инструкции для разработчика; в пользовательском README они не размещаются.

### Проверка окружения в Docker

По требованию владельца зависимости на хост не устанавливаются: сборка, тесты и рендеринг выполняются только в контейнере. Сценарий [tests/environment/check.sh](../tests/environment/check.sh) проверяет окружение на специальных диаграммах; он не задаёт публичный API будущей библиотеки.

Команды выполняются из корня репозитория:

```sh
docker build --tag rulewayuml-dev:plantuml-1.2026.5 \
  --file .devcontainer/Dockerfile .devcontainer

docker run --rm --network none --user vscode \
  --mount "type=bind,source=$PWD,target=/workspace,readonly" \
  --workdir /workspace \
  rulewayuml-dev:plantuml-1.2026.5 \
  bash tests/environment/check.sh
```

В открытом Dev Container достаточно выполнить `bash tests/environment/check.sh`. Временные файлы создаются внутри контейнера; по умолчанию результаты находятся в `/tmp/rulewayuml-check-results`. Вариант с `--rm` удаляет их вместе с контейнером. Для сохранения изображений можно запустить контейнер с выбранным именем без `--rm`, скопировать результаты через `docker cp`, затем удалить только этот проверочный контейнер.

Набор проверок: локальный `!include` и процедура, русские подписи и шрифт DejaVu Sans, роли и условия, параллельные действия, ссылка в SVG, Graphviz, форматы SVG/PNG, пути с пробелами и ненулевой код завершения для ошибочного синтаксиса и отсутствующего include. Ссылка в тестовой диаграмме использует `example.org`: проверяется её наличие в SVG, а не доступность внешнего сайта.

Для интерактивной работы можно заменить последний аргумент `bash tests/environment/check.sh` на `bash` и добавить `-it` к `docker run`. Образ по умолчанию запускает `bash`, поэтому обычный запуск без команды и без интерактивного терминала не является постоянно работающим сервисом. Порты для локального рендеринга не нужны.

Результат проверки от 2026-09-17: исходная база `java:0-17` не собиралась из-за HTTP 404 при установке пакетов Bullseye; замена на `java:3.1.3-17-bookworm` исправила сборку. Собран образ `rulewayuml-dev:plantuml-1.2026.5`. На Linux amd64 / Docker `29.8.0` подтверждены Java `17.0.20.1`, PlantUML `1.2026.5`, Graphviz `2.43.0`, Maven `3.8.7` и Make `4.3`.

Проверки выполнены от `vscode` (UID 1000), без сети и с исходниками только для чтения. Сценарий завершился с кодом `0`, создал корректные SVG/PNG; ошибочный синтаксис и отсутствующий include вернули код `200`. PNG просмотрены: кириллица, роли, подписи, развилка и параллельные действия читаются. Дополнительно проверены вход в интерактивный `bash`, рабочий каталог `/workspace` и завершение сессии. Проверочные контейнеры удалены, образ сохранён для дальнейшей работы. На хосте зависимости не устанавливались.

## Общий стиль регламентов

**Решение владельца от 2026-09-17:** целевой каталог компонентов — `components/`, общие стили задаются централизованно по дизайн-системе. Прежнее предложение размещать библиотеку в `lib/` заменено этим решением. Первоначальный `main_template.puml` был переименован в `regulation_style.puml`; 2026-09-19 владелец выбрал короткое имя `style.puml`, поскольку назначение проекта уже понятно.

**Уточнение владельца от 2026-09-19:** в левом верхнем углу схемы остаётся только отдельный фирменный знак без надписи Ruleway или RulewayUML. Название библиотеки в марке создаёт лишний визуальный шум. Для марки используется существующий `ruleway-icon.svg`; полные логотипы в README и дизайн-системе не меняются.

Стиль реализован как подключаемое оформление без `@startuml` / `@enduml` и без данных конкретного процесса. Минимальное использование из файла в `examples/`:

```plantuml
@startuml
!include ../components/style.puml
title Название регламента
start
:Выполнить действие;
stop
@enduml
```

Готовый пример — [examples/basic_regulation.puml](../examples/basic_regulation.puml). Обязательных параметров у стиля нет. Автор регламента задаёт заголовок, роли, действия, переходы и пояснения стандартным синтаксисом PlantUML. Для использования вне репозитория достаточно перенести весь `components/` вместе с `assets/` и указать путь к `style.puml`. Отдельная копия только файла стиля не содержит ресурса марки. Верхний колонтитул `header` занят логотипом; название регламента следует задавать через `title`. Старое имя не сохраняется как псевдоним; существующие подключения нужно заменить на `!include ../components/style.puml` с учётом расположения исходника.

Оформление проверено на PlantUML `1.2026.5`:

- DejaVu Sans с поддержкой кириллицы; основной размер текста — 14, заголовка — 22.
- Фон `#F5F8F7`, текст `#142D3B`, белые карточки шагов, линии и переходы `#087F74`, примечания и выделенные области `#E5F5F1`. Акцент `#2DD4BF` в дизайн-системе предназначен для тёмных поверхностей и в текущей светлой теме не используется.
- Единые настройки действий, условий, стрелок, начала и завершения, параллельных ветвей, дорожек ролей, групп, примечаний, заголовка, подписи, легенды и нижнего колонтитула. У действий есть скругление и перенос длинного текста с `MaximumWidth 300`.
- Марка — отдельный знак из `ruleway-icon.svg`, экспортированный в PNG 48 × 48 и встроенный как `data:image/png;base64` в `components/assets/ruleway_logo.iuml`. Это сохраняет фирменную форму, градиент, пропорции и свободное поле, без надписи с названием библиотеки; после экспорта схема не обращается к внешним файлам или сети. Внутренняя переменная — `$ruleway_logo_data`, префикс ресурсов — `ruleway_`.

Растровая копия выбрана после проверки: прямое подключение SVG не отображало логотип в PNG, а встроенный SVG-спрайт искажал знак. Исходные материалы бренда сохранены без изменений. Сама схема в SVG остаётся векторной, марка внутри неё — растровая. Поддержка оформления проверена для диаграмм деятельности в SVG/PNG; другие типы UML и форматы экспорта этой проверкой не охвачены.

Для обновления марки сначала изменяют исходный SVG, затем **только во временном контейнере** экспортируют его командой `rsvg-convert --width 48 --height 48 --keep-aspect-ratio docs/ruleway_design/ruleway-icon.svg --output /tmp/ruleway_logo.png`, кодируют PNG в Base64 и обновляют значение `$ruleway_logo_data`. В комментарии ресурса обновляют SHA-256 исходного SVG. Конвертер `rsvg-convert` из пакета `librsvg2-bin` устанавливается только во временный контейнер, для обычного рендеринга он не нужен.

Проверка примера из корня репозитория в уже собранном окружении:

```bash
docker run --rm --network none --user vscode \
  --mount "type=bind,source=$PWD,target=/workspace,readonly" \
  --workdir /workspace \
  rulewayuml-dev:plantuml-1.2026.5 bash -lc '
    plantuml -charset UTF-8 -checkonly examples/basic_regulation.puml &&
    plantuml -charset UTF-8 -failfast2 -tsvg -o /tmp/ruleway-template-results examples/basic_regulation.puml &&
    plantuml -charset UTF-8 -failfast2 -tpng -o /tmp/ruleway-template-results examples/basic_regulation.puml
  '
```

Для сохранения изображений используют именованный контейнер без `--rm` и `docker cp`, как при проверке окружения. Новые зависимости на хост не устанавливаются.

## Рабочее техническое направление

Следующие пункты — стартовое предложение для реализации, а не утверждённый API:

- Использовать текстовые файлы PlantUML и подключаемые модули; общие определения выносить в библиотеку, содержимое конкретного регламента — в пользовательский исходник.
- Проверить реализацию компонентов через `!include`, `!procedure` и `!function`, описанные в [документации препроцессора PlantUML](https://plantuml.com/preprocessing).
- Сохранять совместимость со стандартными конструкциями [диаграмм деятельности](https://plantuml.com/ru/activity-diagram-beta); сначала проверить представление ролей, условий и групп на небольших примерах.
- Разделять содержание регламента и оформление. Цвет не должен быть единственным носителем смысла.
- Для первого прототипа использовать локальное подключение библиотеки и SVG как рабочий формат просмотра; проверять кириллицу, переносы и ссылки. Способ распространения и поддерживаемые форматы результата пока не утверждены.

Принятая структура: `components/` для подключаемых определений и оформления, `examples/` для самостоятельных пользовательских примеров, `tests/` для проверок и `docs/` для документации. Все эти каталоги существуют. В `tests/environment/` подготовлены проверки окружения. Имена и параметры предметных компонентов и процедур ещё предстоит определить; внутренние ресурсы стиля используют префикс `ruleway_`.

Фирменный ориентир — существующая палитра Ruleway: `#142D3B` (глубокий синий), `#087F74` (бирюзовый), `#2DD4BF` (светлая бирюза), `#E5F5F1` (светлая мята), `#F5F8F7` (светлый фон), `#FFFFFF` (белый). Источник — [описание дизайна](ruleway_design/README.md). Светлая тема реализована в `style.puml`; читаемость проверена на пользовательском примере и расширенной проверочной диаграмме.

С 2026-09-17 README оформлен с использованием существующих `ruleway-logo.svg` и `ruleway-logo-reversed.svg`: `<picture>` выбирает логотип по светлой или тёмной теме среды просмотра. Использованы слоган из дизайн-листа и краткая навигация. Дополнительных изображений, CSS и зависимостей проекта для оформления не введено. Внешний вид проверен локально в двух темах и на экране шириной 390 px; отображение на GitHub отдельно не проверялось.

По уточнению владельца от 2026-09-17 README предназначен для пользователя, который хочет применять практики и компоненты. В нём остаются назначение, практические принципы описания регламентов, планируемый набор компонентов и краткое указание их готовности. Настройка окружения, история продуктового решения, внутренние документы и подробности работы над проектом хранятся в `AGENTS.md` и этом файле. После появления библиотеки README должен вести к реальным компонентам и пользовательским примерам.

## Предлагаемый первый этап

Это последовательность проверки идеи библиотеки; состав первой версии пока не утверждён.

1. Выбрать один небольшой реальный регламент и определить минимальную карточку шага: действие, ответственная роль, вход, выход и связанная инструкция.
2. Сделать минимальный подключаемый компонент и полный пример с несколькими ролями, условием и обработкой исключения.
3. Проверить расширение шага сроком, контрольной точкой и чек-листом, не теряя читаемости основной последовательности.
4. Проверить отдельными примерами группу шагов и ссылку на дочерний регламент с его входами и выходами.
5. По результатам зафиксировать интерфейс компонентов, ограничения оформления, структуру файлов и команды проверки.

Критерии готовности первого этапа: пример собирается указанной версией PlantUML, роли и переходы читаются однозначно, кириллица и длинные подписи не ломают схему, у компонентов описаны параметры и ограничения, а пользователь может повторить результат по инструкции. Наличие схемы само по себе не доказывает удобство работы по регламенту — это проверяется на выбранном процессе с его автором и исполнителем.
