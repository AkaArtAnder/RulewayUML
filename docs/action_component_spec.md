## 1. Назначение и границы

Компонент описывает действие внутри регламента: что сделать, кто отвечает, какой результат получить, как действовать и в какой срок. Каждое действие имеет идентификатор. Если действие нужно раскрыть в отдельный процесс, в компоненте указывается ссылка на дочерний регламент.

Сохраняется принятый формат библиотеки PlantUML: activity-диаграммы, локальное подключение и общее оформление Ruleway. Последовательность, ветвления и параллельная работа задаются конструкциями диаграммы. По уточнению владельца от 2026-09-22 каждое действие схемы регламента и проверочных примеров компонента оформляется через `$ruleway_action(...)`; обычные узлы `:Действие;` без обязательных полей недопустимы. Компонент описывает правила выполнения; учёт фактических исполнителей, статусов, сроков и результатов не входит в библиотеку.

## 3. Согласованный набор параметров

| Параметр | Содержание | Основание | Заполнение |
| --- | --- | --- | --- |
| Идентификатор | Код вида `РСТ-03`: обозначение регламента, его аббревиатура и номер действия | Формат и правила заполнения согласованы владельцем; см. ниже | Обязательно |
| Наименование | Краткое наименование совершаемого действия, например «Проверить заявку» | Выбрано владельцем; связано с категорией шагов в AFFiNE | Обязательно |
| Ответственная роль | Роль, отвечающая за выполнение действия, например «Согласующий»; подпись в блоке — «Ответственный» | Параметр и подпись выбраны владельцем; ответственная роль прямо предусмотрена в AFFiNE | Обязательно |
| Результат | Описание ожидаемого итога и/или ссылка на шаблон итога с понятным названием | Выбрано и уточнено владельцем; связано с выходами и артефактами в AFFiNE | Обязательно |
| Инструкция / чек-лист | Указания по выполнению действия в форме инструкции или перечня пунктов | Выбрано владельцем; инструкции и чек-листы предусмотрены в AFFiNE | По необходимости |
| Срок / SLA выполнения | Норматив выполнения действия, например «До конца следующего рабочего дня после получения заявки» | Выбрано владельцем; SLA предусмотрен в AFFiNE | По необходимости |
| Ссылка на дочерний регламент | Переход к отдельному процессу, раскрывающему действие подробнее | Подтверждена владельцем; заполняется при необходимости расширения действия | По необходимости |

**Решение владельца от 2026-09-22:** обязательны идентификатор, наименование, ответственный (ответственная роль) и результат. Инструкция/чек-лист, срок/SLA и ссылка на дочерний регламент необязательны и включаются независимо друг от друга по необходимости. Действие с четырьмя обязательными полями соответствует требованиям; остальные поля можно не заполнять.

Все семь параметров представлены в API. Необязательные поля по умолчанию пусты и скрываются вместе со своими подписями и отступами. Существующая реализация соответствует утверждённой обязательности; состав параметров и API не изменяются.

### Правила заполнения идентификатора

**Согласовано владельцем 2026-09-22.** Вид: `РСТ-03`.

1. Первый символ всегда **`Р`** — кириллическая буква, обозначающая регламент.
2. Следующие **два символа** — аббревиатура названия регламента. Автор выбирает её в начале работы над регламентом и использует в идентификаторах его действий. Например, `СТ` — «Сущности трекера».
3. После аббревиатуры ставится дефис **`-`**.
4. После дефиса указывается **двузначный номер действия**, задающий общий порядок действий в регламенте. Однозначный номер записывается с ведущим нулём: `03`.

Таким образом, `РСТ-03` обозначает действие № 03 регламента «Сущности трекера». Для учебного регламента «Согласование заявки» в этом ТЗ используется выбранная для примера аббревиатура `СЗ` и код `РСЗ-03`.

Номер отражает общий порядок; ветвления, возвраты и параллельная работа по-прежнему описываются связями диаграммы. В API идентификатор передаётся строкой; его структура проверяется. Нумерация, её уникальность и соответствие порядку остаются ответственностью автора.

### Смысловые уточнения

- **Результат** может быть документом, принятым решением или изменением состояния. Ссылка на шаблон находится в этом же параметре; отдельное поле материалов сейчас не вводится.
- **Инструкция / чек-лист** — один строковый параметр: связный текст или пункты, разделённые `%newline()`. Номера пунктов задаёт автор.
- **Срок / SLA** содержит правило выполнения. Точку отсчёта и рабочий календарь можно уточнить непосредственно в тексте норматива; отдельных параметров для них сейчас нет.
- **Дочерний регламент** раскрывает действие в отдельный процесс. Ссылка должна иметь понятное название; автоматическое встраивание или исполнение дочернего процесса не входит в текущую задачу.
- **Идентификатор** заполняется по согласованным правилам выше. Это отображаемый код действия, а не имя публичной процедуры PlantUML; автоматическая нумерация пока не принята в требования.

## 4. Отложенные параметры

В первую версию не входят отдельные поля краткого описания, других участников, входов, условий начала, критериев завершения, контроля, метрик, исключений, общих материалов и терминов. Не нужно добавлять для них пустые секции, аргументы или заготовки API.

Возврат к любому из этих параметров возможен при конкретной потребности. Тогда обновляются ТЗ и контекст задачи. Отложенные поля не являются обязательной оставшейся работой текущей версии.

## 5. Учебный пример заполнения

Пример продолжает тему существующего `examples/basic_regulation.puml`. Это вымышленные правила для обсуждения и дальнейшей проверки, не утверждённый реальный регламент и не макет дизайна.

| Параметр | Пример |
| --- | --- |
| Идентификатор | `РСЗ-03` — действие № 03 регламента «Согласование заявки» |
| Название | Проверить заявку |
| Ответственная роль | Согласующий |
| Результат | Заключение о полноте заявки с перечнем замечаний при их наличии; при необходимости — именованная ссылка на шаблон заключения |
| Инструкция / чек-лист | Проверить цель заявки; проверить обязательные разделы; сверить комплект документов; сформулировать заключение |
| Срок / SLA | До конца следующего рабочего дня после получения заявки, по рабочему календарю организации |
| Ссылка на дочерний регламент | Не задана для простого действия; если проверка раскрывается в отдельный процесс — ссылка «Проверка заявки» |

Для результата допустим и краткий вариант: именованная ссылка «Шаблон заключения». В реализации проверка заявки получила код `РСЗ-02` согласно порядку основного примера. Используются локальные [шаблон заключения](../examples/materials/review_template.html) и [дочерний регламент](../examples/review_regulation.puml); переходы проверены в SVG через браузер.

| Область | Результат |
| --- | --- |
| Состав | Семь строковых параметров; дополнительные поля не введены |
| Идентификатор | Кириллица и ведущий ноль сохраняются; неверный префикс, недвузначный и нечисловой номер вызывают ошибку Ruleway |
| Результат | Проверены описание, именованная ссылка и их сочетание |

| Логика схемы | Проверены две дорожки, условие, цикл и параллельные ветви; все пять действий в `action_flow.puml` оформлены компонентом |
| SVG/PNG | Синтаксис и рендеринг шести схем успешны, PNG просмотрены; знак встроен, кириллица читается, обрезки текста нет |
| Навигация | SVG основного и дочернего примеров открыты браузером Codex по localhost HTTP; ссылки на шаблон, дочерний процесс и обратно проверены кликами |
| Переносимость | Отдельная копия только `components/`, путь с пробелами и другой рабочий каталог проверены без сети |
| Регрессии | Проверки окружения и рендеринг трёх исторических макетов дизайна пройдены |
| Документация | Описаны подключение, параметры, пустые значения, формат ID, разметка и ограничения; пользовательский пример обновлён |

Применимость подтверждена на учебных схемах: понятны действие, ответственный, результат, порядок и норматив; длинные инструкции увеличивают высоту. Реальный утверждённый регламент и пользовательское исследование не проверялись. PNG не даёт кликабельности; `file://`, wiki, AFFiNE и другие среды публикации отдельно не проверены.
