Владелец попросил пояснить, предполагается ли процедура с правилами заполнения условия, и показать её применение на примерах. Подготовить проверяемый прототип и реальные изображения PlantUML для обсуждения. Это разрешение на примеры и прототип; публичный API и состав требований ещё не утверждены.

- Рендеринг выполняется в Docker на версии из Dockerfile (`1.2026.5`); временные результаты размещаются вне исходников.

## Решение для прототипа и результат

- Добавлены [материалы прототипа](../design/condition_component/README.md) и `condition_prototype.iuml` с одной функцией `$ruleway_condition($question, $basis)`. Она возвращает подпись для стандартных конструкций, что позволяет одинаково использовать её в `if` и `repeat while` без набора обёрток управления потоком.
- В прототипе обязательны вопрос и основание для ответа. Ответственный и работа по проверке остаются в действии; новый ID условия не введён. Это предложение по заполнению, не утверждение публичных требований.
- Три самостоятельных примера: `decision.puml` — согласование/отказ с уведомлением; `rework.puml` — подготовка и повторная проверка до отсутствия замечаний; `long_condition.puml` — многострочный критерий и основание в цикле комплекта документов. Каждая схема содержит три действия через `$ruleway_action`.
- Два сценария согласования — отдельные учебные иллюстрации, не изменения основного регламента. Отказ показан только в первом. Второй охватывает подготовку до передачи на согласование; лимит повторов не придуман.
- Начальный рендер длинного текста показал буквальные закрывающие теги после переносов. Форматирование применено отдельно к каждой строке; все три схемы повторно проверены и просмотрены.
- `components/`, `examples/`, ТЗ действия и пользовательская спецификация не менялись. Общий контекст и AGENTS.md описывают новый каталог именно как прототип.
