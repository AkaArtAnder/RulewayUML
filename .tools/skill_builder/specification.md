# Скилл RulewayUML: проект спецификации первой версии

Актуализировано: 2026-09-23. Статус: техническая реализация `0.1.2-dev` использует единую принятую версию PlantUML `1.2025.10` для Wiki и браузера; отдельные профили удалены. Пользователь подтвердил визуальную проверку перехода окружения; три поведенческих сценария и кликабельность в Wiki проверяются отдельно.

Контекст и решения: [основной контекст](../../docs/context.md), [задача скилла](../../docs/tasks/2026_09_22_agent_skill.md). Действующий API: [руководство библиотеки](../../docs/specification/README.md).

## 1. Основания и статус требований

**Запрос владельца:** локально подключаемый скилл для ИИ-агента; три сценария — схема по готовому регламенту в личном формате пользователя, помощь в написании регламента с нуля и редактирование уже существующей схемы, соответствующей RulewayUML. Итоговые результаты — исходник для вставки и SVG для документа. Сценарий редактирования добавлен владельцем при продолжении работы 2026-09-22.

**Действующая основа:** четыре принятых компонента и общий стиль RulewayUML; стандартные переходы PlantUML; существующие правила заполнения, идентификаторов и границ процесса. Эта спецификация не меняет API и не переоткрывает приёмку компонентов.

**Уточнение владельца от 2026-09-22:** скилл предназначен для популярных агентных систем без привязки к одной из них; стандарты оформления можно взять из Codex. Целевые среды использования результата — Яндекс Wiki и HTML в браузере.

**Ответственность за ссылки:** пользователь сам заполняет и меняет адреса при создании или редактировании схемы. Скилл сохраняет заданные адреса и поддерживает кликабельность ссылок в выбранном представлении; подбор адресов, проверка доступности ресурсов и прав доступа не входят в его задачи.

**Постоянные ID — решение владельца от 2026-09-22:** сохранять существующие идентификаторы; новый шаг получает свободный номер. Порядок выполнения определяется только переходами. Это заменяет прежнее требование считать номер в ID порядковым.

**Предложения этого документа:** единый скилл с тремя режимами, промежуточное рабочее описание, состав поставки, порядок проверки и учебные сценарии. Три сценария заданы владельцем; конкретная методика их реализации остаётся проектом. Разрешение начать работу не трактуется как утверждение всех деталей. Решения о средах и распространении фиксируются отдельно.

В этот объём не входят исполнение процесса, контроль фактических сроков, учёт выполненных действий или самостоятельное приложение. Новый формат ввода, новая база данных и расширение полей компонентов для работы скилла не требуются.

Среда без доступа к локальному запуску может позволить подготовить описание и исходник, но не обеспечивает весь запрошенный результат. Агент сообщает, что SVG не создан, и сохраняет выполненную работу; наличие файла или успешный рендеринг не имитируются.

### Переносимость между агентами

По [официальному описанию скиллов OpenAI](https://learn.chatgpt.com/docs/build-skills), основа пакета — `SKILL.md` с полями `name` и `description`; дополнительные инструкции, исполняемые помощники и ресурсы размещаются в `references/`, `scripts/` и `assets/`. `agents/openai.yaml` — необязательные метаданные. Предлагается использовать эту структуру, сохраняя предметные инструкции независимыми от Codex.

Для полного сценария агентной среде нужны чтение инструкций и исходных документов, диалог с пользователем, запись файлов, запуск согласованного локального рендерера и просмотр результата либо явно обозначенная передача визуальной проверки пользователю. Эти возможности описываются по назначению, без обязательных названий инструментов, путей установки Codex, MCP-серверов или определённого поставщика модели.

Способы обнаружения и установки скилла в конкретных системах следует описать отдельно при упаковке. Подключение к системе без встроенного формата скиллов может потребовать явной загрузки инструкций и ресурсов. Общая структура пакета не доказывает совместимость со всеми агентами: при проверке фиксируются конкретная система, версия и реально пройденные операции. Это не меняет принятую цель переносимости.

## 3. Общий порядок работы

1. Определить режим: преобразование готового регламента, разработка с нуля или редактирование существующей схемы RulewayUML. Не задавать этот вопрос повторно, если намерение ясно.
2. Получить фактическое содержание доступного источника. Для файла использовать доступное средство чтения; имя файла и метаданные не заменяют содержание. Если существенная часть не прочитана, явно указать пробел.
3. Собрать компактное рабочее описание процесса и список существенных неопределённостей. При редактировании опираться на существующий исходник и выделить область изменений; не начинать описание заново.
4. Уточнить сведения, которые меняют ответственность, обязательный результат, границы или переходы. Параллельно оформлять уже известные части.
5. После разрешения существенных неопределённостей подготовить исходник на действующем API библиотеки. Если данных достаточно, не вводить дополнительную обязательную приёмку перед генерацией.
6. Проверить смысл маршрутов, затем синтаксис, рендеринг и вид результата в рамках доступных инструментов и поручения пользователя.
7. Выдать текст и схему из одной согласованной версии содержания. При последующих правках обновлять затронутые переходы, упоминания ID действий и SVG; адреса ссылок менять только по указанию пользователя. Не выдавать старое изображение за результат нового исходника.

### Рабочее описание

Это средство разбора, а не новый обязательный документ пользователя. Достаточно краткого текста или таблицы:

- Назначение, событие запуска, входы процесса и допустимые исходы.
- Действия: название, ответственная роль, необходимые данные, ожидаемый результат и дополнительные поля по применимости.
- Переходы: откуда, куда, при каком условии; основание решения; точки возврата и ожидания.
- Для готового документа — пункт или фрагмент источника, на котором основано существенное правило.
- Неопределённости и предложения агента, отделённые от сведений пользователя.

Входы шага учитываются при анализе зависимостей, но не становятся новым аргументом `$ruleway_action`. Если пользователь не задаёт формат итогового текста, можно предложить компактное описание границ, ролей, действий, маршрутов и исключений. Введение JSON/YAML-схемы не требуется для первого выпуска.

### Уточнения

Сначала спрашивать о пропусках, которые меняют смысл схемы: кто выполняет действие, что считается результатом, куда ведёт исход, где начинается и заканчивается процесс. В одном сообщении группировать связанные вопросы; не заставлять пользователя заполнять все необязательные поля.

Не придумывать ответственных, сроки, лимиты повторов, критерии отказа, внешние ссылки или правила эскалации. При противоречии показать конкретные фрагменты и объяснить, какие маршруты получатся при разных трактовках. Предложения агента обозначать явно. Истечение времени ожидания ответа не считается согласием.

Черновик может содержать список открытых вопросов, но не должен выдавать незаполненные обязательные поля или предположительные маршруты за завершённый регламент. Отсутствие необязательного SLA само по себе не препятствует выпуску.

Предлагаемый порядок уточнений:

| Что обнаружено | Действие агента |
| --- | --- |
| Неизвестны исполнитель, результат действия или дальнейший путь | Уточнить недостающее правило; продолжать описывать независимые части. |
| В источнике два противоречащих правила | Привести конкретные формулировки и спросить, какое применять; не выбирать по удобству схемы. |
| Не указан SLA, инструкция, ссылка, входы начала или дополнительный результат завершения | Оставить необязательное поле пустым; не превращать отсутствие в обязательный вопрос. |
| Есть правило, но его формулировка длинная | Сократить подпись без изменения смысла; подробности оставить в тексте или инструкции. |
| В редактируемой схеме информация уже есть | Использовать её; спрашивать только о новой неопределённости, возникшей из запроса. |

После ответа уточнять только оставшиеся существенные пробелы. Не повторять весь опрос и не запрашивать отдельное согласование каждого корректно заполненного компонента. Наличие принятого общего правила не исключает вопроса о конкретном противоречии.

## 4. Три режима

### Готовый регламент

Сохранить терминологию, назначение и предметные правила источника. Последовательность разделов не считать автоматически порядком выполнения: восстановить зависимости по данным, результатам и явным указаниям переходов.

Сопоставить существенные действия, условия и исходы с исходным текстом. Длинные инструкции можно сокращать в схеме с сохранением доступа к полному содержанию. Нельзя молча потерять исключение, переименовать роль по смысловому предположению или добавить правило ради удобной компоновки.

Предложения по улучшению процесса приводить отдельно. Переписывать исходный документ целиком только при соответствующем запросе. Для чистого преобразования достаточно схемы и кратких пояснений к преобразованию.

### Разработка с нуля

Начать с цели и границ: что запускает процесс и какой результат должен получить его участник. Затем определить основной маршрут, ответственных и результаты, после чего разобрать альтернативы, доработку и исключения по применимости.

Объяснять выбор компонента на текущем материале пользователя: действие выполняет работу, условие выбирает путь по полученному основанию, начало и завершение описывают границы. Дополнительные поля предлагать там, где они помогают исполнителю.

Собирать итоговое описание постепенно и сохранять уже принятые ответы. После изменения правила пересматривать зависящие от него шаги. Финальный текст оформлять в выбранной пользователем структуре; рабочая таблица не навязывается как единственный формат.

### Редактирование существующей схемы RulewayUML

Вход — доступный исходник `.puml` или код существующей схемы и требуемые изменения. Режим применяется и к схеме, созданной ранее другим агентом или самим пользователем. Если дано только изображение, сначала найти доступный исходник в предоставленных материалах; при его отсутствии уточнить возможность получить код. Восстановление схемы по изображению не выдавать за точное редактирование исходника.

1. Прочитать схему и необходимые локальные подключения, определить используемые компоненты, ID, поля и переходы. Существующие сведения не собирать повторно вопросами. Соответствие RulewayUML не означает автоматическую совместимость с любой версией библиотеки; не обновлять библиотеку или API без связи с запросом.
2. Выделить требуемое изменение: поля действия, добавление/удаление шага, очередность, условие, повтор, границы или оформление. Уточнять только существенные сведения, которых нет в запросе и исходнике.
3. Определить связанные места: при смене результата проверить основание условия; при изменении формулировки вопроса — смысл подписей исходов; при добавлении или удалении шага — входящие и исходящие переходы, повтор и упоминания ID; при смене роли — соответствие дорожке, если она используется.
4. Внести правку в существующий исходник. Сохранить остальные данные, комментарии, локальные подключения и оформление, насколько это совместимо с запросом. Адреса ссылок остаются пользовательскими данными: не заменять их самостоятельно и не открывать целевые ресурсы для проверки доступности.
5. Сохранить ID существующих действий, в том числе при перемещении, смене текста, исполнителя или срока. Новому действию дать свободный номер; вставка и удаление не вызывают перенумерацию остальных. Не менять формат ID и не добавлять счётчик в компонент. Если пользователь отдельно поручил заменить конкретный ID, обновить его упоминания в доступном исходнике.
6. Сравнить версию до и после правки: изменения соответствуют запросу, связанные основания и переходы согласованы, незатронутые маршруты сохранены. Если отдельно дан текст регламента и поручено его редактирование, синхронизировать затронутые фрагменты; наличие схемы само по себе не является поручением переписать весь текст.
7. Проверить затронутую диаграмму по общему порядку и сформировать новый SVG из итогового исходника. Выдать полный обновлённый код для вставки, файл `.puml`, SVG и краткое описание смысловых изменений. При ошибке экспорта сохранить правку исходника и явно сообщить, что новое изображение не создано.

Полное преобразование чужой нотации в RulewayUML не подразумевается этим режимом. Обнаруженные несвязанные недостатки можно обозначить отдельно, не превращая локальную правку в переработку всего регламента.

## 5. Правила компонентов и маршрутов

Точные параметры и ограничения берутся из существующих описаний [действия](../../docs/specification/components/action.md), [условия](../../docs/specification/components/condition.md), [начала](../../docs/specification/components/start.md) и [завершения](../../docs/specification/components/end.md). При упаковке требуется согласованная версия этих правил и реализации.

| Ситуация | Правило для агента |
| --- | --- |
| Действие | Все действия через `$ruleway_action`: обязательны ID, название, ответственный и результат. Инструкция, SLA и подрегламент независимы и необязательны. |
| Размер действия | Название обозначает понятную работу. Смена ответственного, отдельный передаваемый результат или развилка — основания рассмотреть разделение; пункты одного чек-листа не требуют отдельных узлов автоматически. |
| Последовательность | Необходимые данные должны существовать к началу использующего их действия: приходить извне или из предшествующего результата. Проверить доступность на каждом применимом маршруте. |
| Условие | Вопрос и основание обязательны; основание доступно к моменту выбора. Проверка и ответственный остаются в предшествующем действии. Исходы подписаны; неизвестный ответ не означает «нет». |
| Повтор | Явные причина, точка возврата и условие выхода по последней проверке. Заданный лимит включает путь при его достижении. Не добавлять лимит, если источник его не устанавливает. |
| Параллельность | Независимость обосновывается результатами и зависимостями, а не разными ролями. До построения маршрута определить, каких ветвей ждёт продолжение. Неполученный обязательный результат не считать успешным завершением. |
| Ожидание | Определить событие продолжения. Срок ожидания и путь при неполучении ответа отражать только при наличии такого правила; при смысловой неопределённости уточнить его. |
| Подрегламент | Связать вход, возвращаемый результат и условие продолжения; предусмотреть неуспех, если он установлен. Ссылка сама по себе этих правил не задаёт. |
| Границы | Явные `start`/`stop` и подписи через публичные функции в `note right`. Авторские событие и исход без встроенного словаря. Доработка не означает конец всего регламента. |
| Дорожки | Использовать по пользе для чтения; ответственный остаётся в действии. Общего обязательного выбора схем с дорожками или без них нет. |

### Формирование одного действия

1. Выделить работу и её границы: что получает исполнитель, что делает и что передаёт дальше. Вход нужен для понимания зависимости, но не добавляется в API действия.
2. Сформулировать название как действие с предметом: «Проверить комплект документов». Сохранять термины источника; не требовать разных блоков только из-за нескольких глаголов, если это единая работа одной роли с одним результатом.
3. Назвать ответственную роль из источника или ответа пользователя. Если пункт объединяет работу нескольких ролей, разобрать передачу результата и выделить самостоятельные действия там, где она происходит.
4. Описать результат как наблюдаемый итог работы: полученный документ, запись, решение или состояние. Для готового регламента не придумывать новый обязательный документ ради такого описания. Например, «Проверить заявку» — работа, а «Замечания зафиксированы» — возможный результат, если это соответствует правилам пользователя.
5. Перенести критерии и конкретные операции в инструкцию, если они заданы. SLA заполнять только по имеющимся данным; если задано «два дня», но точка отсчёта влияет на исполнение и неизвестна, уточнить её. Отсутствующий срок не запрашивать только ради заполнения поля.
6. Оформить каждый получившийся шаг через действующий компонент. Обязательные поля не заменять пробелами или фиктивными заглушками; адреса ссылок не изобретать. ID новых действий назначать после определения состава шагов; существующие ID сохранять. Номер не используется для восстановления маршрута.

Пример разбиения: «Автор готовит материал, редактор проверяет его, автор исправляет замечания» содержит передачу работы между ролями и повтор; одной инструкции внутри блока автора недостаточно. Напротив, проверка трёх пунктов комплекта одной ролью может оставаться чек-листом одного действия, если между пунктами нет самостоятельных переходов или передач.

### Восстановление очередности процесса

Работать сначала со смыслом переходов, затем с расположением в исходнике:

1. Установить событие запуска и данные, доступные до первого действия. Если первое действие создаёт заявку, событие начала не должно без основания предполагать уже готовую заявку.
2. Для каждого действия определить необходимые данные и откуда они поступают: из входов процесса, результата другого действия или явно описанного внешнего события. Не считать зависимость существующей только из-за близости пунктов в документе.
3. Построить основной маршрут по этим зависимостям. Совпадение ролей не требует соседства действий, а разные роли сами по себе не означают параллельность.
4. Разместить выбор пути после получения его основания. При объединении альтернатив проверить, что продолжение получает необходимые данные из каждой приходящей ветки; результат, получаемый только в одной ветке, не считать общим автоматически.
5. Добавить возвраты с явным адресатом доработки и повторной проверкой. Уточнить, должен ли участок выполняться хотя бы один раз: нельзя заставлять его выполняться первым проходом только потому, что это удобно для стандартного `repeat`. Входную проверку, если она предусмотрена, можно выразить стандартным условием без нового API.
6. Разбирать параллельные ветви через независимость работ и правило объединения результатов. Если источник не определяет, нужно ждать все результаты или достаточно одного, уточнить это до финализации соответствующего участка.
7. Разместить каждый конечный исход после обязательных действий этого пути, включая передачу или получение результата, если они входят в регламент. Конец дочерней схемы сопоставить с продолжением родительского процесса.

Обратный переход допустим как часть описанного цикла. Замкнутый участок без установленного условия выхода или пути при заданном ограничении — предметный вопрос, а не повод убрать обратную стрелку. Агент проверяет описанные правила завершения; фактическую сходимость реальной работы не гарантирует.

### Формирование подписей условия и границ

- Вопрос условия должен различать предусмотренные маршруты по конкретному основанию. Для каждого ответа отдельно сформулировать, куда он ведёт. При отрицании или инверсии вопроса проверить оба перехода, даже если имена действий не менялись.
- Основание может быть результатом действия, документом или правилом. Для результата действия указать его ID и название; при переименовании результата синхронизировать это упоминание. Число ответов и случаи неизвестного ответа определяются содержанием регламента, а не желанием свести всё к одному ромбу.
- Событие начала фиксирует наступившую причину запуска; входы добавляются по необходимости. Название всего процесса само по себе не заменяет событие.
- Исход завершения фиксирует достигнутое состояние. Дополнительный результат описывается, если он полезен; отдельное действие по уведомлению или передаче не заменяется примечанием у `stop`.

### Нумерация и структурные изменения

ID сохраняет согласованный формат: кириллическая `Р`, два символа выбранной аббревиатуры, дефис, две цифры. По решению владельца ID постоянен и уникален в пределах регламента; число служит различению действий, а не обозначает очередь исполнения. Маршрут определяется только переходами.

Правило применяется одинаково к последовательным, альтернативным и параллельным действиям:

- Сохранять ID при редактировании и перемещении действия; добавление или удаление соседнего шага не меняет остальные ID. Не сортировать исходник по числовой части и не переставлять ветви ради возрастающих номеров.
- Для нового действия выбрать номер, не занятый другим действием этого регламента. Пример: при существующих `РСЗ-01`, `РСЗ-02`, `РСЗ-03` новый `РСЗ-04` можно разместить между `РСЗ-01` и `РСЗ-02`; последовательность `01 → 04 → 02 → 03` допустима.
- Каждый узел цикла имеет один ID; повторное выполнение не создаёт новый номер. Условие, начало, завершение и стрелка ID действия не получают. Отдельная дочерняя схема имеет собственные идентификаторы регламента.
- При удалении действия проверить упоминания его ID и связанные переходы. Если удалён источник основания условия, уточнить или исправить соответствующее правило по запросу; простой замены номера недостаточно.
- При разделении одного действия или объединении нескольких определить, какое действие сохраняет прежнюю идентичность, а какие являются новыми. Когда это неясно из запроса, уточнить именно эту связь; не переносить старый ID на другую работу молча.
- Выбор номера записывается в исходник явно. Генератор ID, счётчик в компоненте и скрытая перенумерация в библиотеку не добавляются. Если свободного двузначного номера нет, обсудить осмысленное выделение подрегламентов либо отдельное изменение формата.

Предлагаемый приём выбора свободного номера: для новых схем начинать с `01`, а при добавлении сначала рассмотреть следующий номер после наибольшего известного. Известные ранее удалённые ID не назначать другой работе. Это рекомендация скиллу, а не дополнительная проверка компонента; отдельного реестра истории ID в первой версии не требуется. Если история не предоставлена, не обещать проверку уникальности относительно всех прошлых редакций.

### Проверка содержания перед экспортом

Перед выдачей пройти основной маршрут, каждую альтернативу и хотя бы один повтор; по применимости — достижение заданного лимита, неуспех дочернего процесса и неполученный результат параллельной ветви. Для каждого пути должны быть понятны ответственные, основания, результаты и продолжение. Успешный рендеринг не доказывает смысловую корректность.

На каждом пути проверить три вопроса: доступно ли основание для следующего шага, получен ли требуемый результат и понятен ли следующий переход. При редактировании дополнительно сравнить смысл до и после правки: намеренные изменения отражены, остальные пути не получили новых условий или исходов.

Признаки готовности содержания: обязательные поля заполнены, все предусмотренные исходы имеют продолжение или завершение, ссылки условий на результаты согласованы, существенные противоречия разрешены. Отсутствие необязательных полей, пользовательских адресов или доступа к ресурсам по ссылкам не препятствует подготовке результата. Если содержательная неопределённость остаётся, выдать известную часть как черновик и назвать конкретный незавершённый участок.

### Образцы сложных маршрутов

По уточнению владельца часть действий в образцах должна демонстрировать все семь параметров, включая срок/SLA. В `РПВ-01` и `РПМ-02` заполнен полный набор; дополнительные действия показывают сроки с точкой отсчёта и неполные наборы необязательных полей. Это требование к наглядности учебных образцов, а не обязательность всех полей для каждого пользовательского действия. Учебные сроки не становятся значениями по умолчанию для скилла.

В [каталоге кандидатов для скилла](scenarios/README.md) подготовлены четыре образца на существующих компонентах: параллельное получение двух результатов, ожидание внешнего ответа до заданного срока, получение отсутствующего основания и обработка результата дочернего регламента. Последний образец состоит из двух самостоятельных схем. Для каждого описаны учебные предпосылки, ожидаемые пути и вопросы, которые нельзя решать за автора реального регламента.

Образцы показывают различие между отсутствующим и отрицательным ответом, выполненной проверкой с замечаниями и невозможностью проверки, завершением дочернего и основного процессов. Свободные ID `РДО-05` и `РПМ-05` расположены по переходам, без перенумерации остальных действий. Ссылки между двумя схемами учебные; адреса в пользовательском регламенте заполняет сам пользователь.

Владелец подтвердил корректное отображение всех схем. Исходники включены в первую сборку с адаптацией путей подключений; их экспорт проверен на копии вне репозитория. Они дополняют три сценария проверки поведения из раздела 7 и не устанавливают новых предметных правил библиотеки. Это не означает завершение проверки поведения скилла.

## 6. Результат и требования к экспорту

Предлагаемый основной комплект: `.puml`, код этого исходника для копирования, SVG и полный каталог `components/`. Предоставленные для включения локальные материалы и созданные в рамках запроса дочерние схемы добавляются по необходимости; скачивать ресурсы по ссылкам для комплектования результата не требуется. При разработке с нуля добавляется итоговый текст в выбранном формате. Если пользователь уже имеет подходящую библиотеку, достаточно явно указать её версию и способ подключения.

При редактировании выдаются обновлённые исходник и SVG вместе с кратким перечнем изменений. Изображение должно соответствовать новой редакции; исходную библиотеку не заменяют новой копией только ради упаковки результата.

Адреса задаёт пользователь. Отсутствие адреса не блокирует подготовку схемы: результат действия описывается текстом, необязательная ссылка пропускается до её заполнения. Скилл не подбирает и не переписывает адреса самостоятельно, не проверяет доступность целевых ресурсов и права читателей. Проверка экспорта касается сохранения заданного адреса и возможности нажать ссылку, а не содержимого ресурса по ней.

Код с `!include` пригоден для среды с доступными зависимостями. Для запрошенного кода для вставки первая реализация дополнительно выдаёт `_portable.puml` — результат штатного препроцессора PlantUML без локальных подключений. Он проверен повторным рендерингом отдельно от библиотеки; редактируемым оригиналом остаётся версия с вызовами RulewayUML. Не обещать работу кода в произвольном онлайн-редакторе.

### Яндекс Wiki и HTML

В [документации Яндекс Wiki](https://yandex.ru/support/wiki/ru/wysiwyg/diagrams) описан встроенный блок PlantUML. Это отдельный способ размещения исходного кода: версия движка и совместимость с функциями и стилями RulewayUML на открытой странице не установлены. Локальные пути `!include` из пользовательского комплекта не обеспечивают доступ к этим файлам в Wiki. Первая реализация выдаёт развёрнутый исходник для вставки; его работу ещё нужно проверить в целевом блоке.

[Инструкция Wiki по изображениям](https://yandex.ru/support/wiki/ru/wysiwyg/images) описывает загрузку и вставку по ссылке, но не подтверждает на этой странице конкретно SVG RulewayUML и переходы внутри него. План проверки: загрузить подготовленный SVG в согласованную тестовую страницу, проверить показ, масштаб, кириллицу, знак и открытие оригинала; отдельно проверить техническую кликабельность на учебных ссылках. Пользовательские ресурсы для этой проверки не требуются. До такой проверки поддержка SVG в Wiki остаётся целевым требованием, а не установленным результатом.

Для HTML первая реализация выдаёт статическую страницу с SVG внутри `<object>` и прямой ссылкой на SVG. Пропорции блока берутся из `viewBox`; переходы к учебному шаблону и дочерней схеме проверены в локальном браузере. По [документации PlantUML](https://plantuml.com/svg), ссылки внутри SVG при включении через `<img>` не работают как при непосредственном размещении SVG в HTML. Поэтому различать показ картинки и навигацию: для первого проверить `<img>` с открытием оригинала, для второго — встраивание SVG как документа и разрешение учебных ссылок относительно SVG. Пользовательские адреса сохраняются без самостоятельной замены.

Скилл подготавливает файлы и инструкции размещения. Публикация в Wiki, загрузка пользовательских материалов и выбор внешнего хостинга не следуют автоматически из запроса создать схему. Предпросмотр HTML — статический пример использования результата, а не новое приложение.

Требования к локальному экспорту:

- SVG получается из выданного исходника посредством PlantUML закреплённой версии.
- Пути подключения библиотеки переносимы между каталогами. Адреса пользовательских ссылок сохраняются; наличие файлов по этим адресам не является условием экспорта. Исходники пользователя не перезаписываются побочными результатами.
- Ошибка разбора или рендеринга сообщается явно; старый SVG и изображение ошибки не выдаются за готовую схему.
- Команда работает в согласованном контейнерном окружении. Наличие Docker и доступ агента к запуску проверяются отдельно от наличия скилла; зависимости на хост в рамках проекта не устанавливаются.
- Читаемость оценивается при фактической ширине вставки: кириллица, переносы, обрезка, плотность и размеры текста. При чрезмерном размере предлагается обзор с дочерними схемами без потери правил.
- Проверяется отображение знака: внутри стиля используется векторный SVG-спрайт 48 × 48 из залитых контуров, включая приближение градиента. Профиль Wiki отклоняет растровые вставки и несовместимые теги выравнивания.
- Техническая кликабельность проверяется в выбранной среде отдельно от изображения, на учебных ссылках. Доступность пользовательских ресурсов не проверяется. Существующая проверка SVG по localhost HTTP не доказывает работу ссылок внутри документа.

В финальном ответе агент кратко указывает, какие смысловые и технические проверки действительно выполнены, где лежат результаты и какие ограничения остались. Перечень поддерживаемых сред пополняется по фактической проверке.

## 7. Учебные сценарии для проверки поведения

Это подготовленные примеры будущей проверки, а не реальные документы владельца и не результаты запуска скилла. Содержание сценариев не устанавливает предметные правила для других регламентов.

### Сценарий А: готовый регламент в авторском формате

**Запрос пользователя:** «Построй схему по этому описанию согласования заявки. Порядок разделов оставлен как в моей памятке».

**Исходный текст:**

1. «Завершение. После согласования инициатор получает решение и принимает его к работе. На этом регламент заканчивается».
2. «Проверка. Согласующий проверяет заявку и составляет заключение с замечаниями либо отметкой об их отсутствии. При замечаниях инициатор исправляет заявку и передаёт её на повторную проверку».
3. «Запуск. У инициатора возникает потребность в согласовании. Инициатор готовит заявку с документами и передаёт согласующему».
4. «Решение. Если в последнем заключении замечаний нет, согласующий фиксирует решение о согласовании и передаёт его инициатору».

**Ожидаемое поведение:** восстановить запуск, подготовку, проверку, цикл исправления, решение и получение результата; сослаться на соответствующие пункты. Основание выхода из цикла — последнее заключение. Конец расположен после получения решения, а не после первой проверки. Отдельные или объединённые подготовка/доработка допустимы при сохранении этих маршрутов и ответственности.

**Что нельзя добавлять:** отказ, срок, числовой лимит доработки, новую роль или вымышленный шаблон документа. Отсутствующие необязательные поля не заполняются предположениями. Аббревиатуру для ID можно предложить как техническое обозначение, не меняя предметные правила.

**Критерии проверки:** каждый существенный пункт представлен; раздел «Завершение» не стал первым действием; замечания возвращают к исправлению и повторной проверке; положительный маршрут достигает получения решения. Выданный SVG соответствует исходнику. Автоматический способ установления смыслового соответствия здесь не заявляется.

### Сценарий Б: регламент создаётся с нуля

**Начальный запрос:** «Помоги описать согласование внутренней статьи. Автор готовит текст, редактор проверяет. Иногда надо исправить. В итоге нужен текст регламента и схема».

**Ожидаемый первый разбор:** известны роли, подготовка, проверка и доработка; неизвестны границы, фиксируемое основание проверки и окончательный результат. Уточнить их до объявления финального маршрута. Не предполагать, что редактор публикует статью.

**Учебные ответы для последующего диалога:**

- Запуск — автор получил согласованную тему и исходные материалы. Публикация находится вне этого регламента.
- Редактор оформляет заключение: перечень замечаний или отметка «готово к публикации».
- Автор исправляет текст; редактор проверяет новую редакцию и обновляет заключение.
- При отсутствии замечаний редактор передаёт автору текст с отметкой готовности, автор получает его. Это завершает процесс.
- Ограничение числа повторов и норматив срока в этом учебном регламенте не установлены.
- Итоговый текст нужен разделами «Назначение», «Участники», «Порядок работы», «Результат».

**Ожидаемый результат:** описание в выбранной структуре, схема с ответственными и результатами, цикл по последнему заключению, завершение после получения автором текста с отметкой готовности. Передачу можно описать в действии редактора; она не должна исчезнуть за подписью завершения.

**Критерии проверки:** агент использует полученные ответы, не спрашивает их повторно, не добавляет публикацию, сроки и лимиты; объясняет выбор компонентов на примере пользователя. Если ответа о конечном результате нет, продолжает работу с известной частью и обозначает незавершённую границу, а не выдумывает её.

### Сценарий В: редактирование существующей схемы

**Исходный материал:** копия [основного примера без дорожек](../../examples/basic_regulation_no_lanes.puml) с его локальными подключениями. В нём четыре действия `РСЗ-01`–`РСЗ-04`, цикл проверки, вопрос «В заключении есть замечания?» и ссылки на шаблон и подрегламент. Проверку сценария проводить на копии; сам публичный пример в рамках разработки скилла не изменяется.

**Запрос пользователя:** «В действии РСЗ-02 укажи срок 2 рабочих дня после получения. Переформулируй условие цикла: “Заключение без замечаний?”. Смысл маршрутов сохрани: при замечаниях возвращаемся на доработку, без замечаний идём на согласование. ID, адреса ссылок и остальные поля не меняй».

**Ожидаемое поведение:** прочитать имеющуюся схему, изменить SLA только у `РСЗ-02` с сохранением точки отсчёта и обновить вопрос. Из-за смены смысла вопроса ответ «нет» теперь возвращает в цикл, а «да» ведёт к согласованию. Основание остаётся «РСЗ-02: заключение»; остальные действия, границы, поля, адреса и оформление сохраняются.

**Критерии проверки:**

- Полный набор ID и четыре действия сохранены; остальные сроки не изменены.
- Замечания по-прежнему ведут к доработке и повторной проверке; отсутствие замечаний — к согласованию и получению решения.
- Агент поменял подписи исходов вместе с вопросом. Одна лишь замена текста вопроса с прежними «да/нет» считается ошибкой.
- Адреса ссылок сохранены, проверки доступности пользовательских ресурсов не выполнялись.
- Не изменены компоненты библиотеки и публичный пример; пользователь получает обновлённую копию исходника и соответствующий ей SVG.
- Краткое описание правки называет изменение срока и переформулировку вопроса с сохранением маршрутов. О выполненном рендеринге сообщается только при фактическом успешном запуске.

Этот сценарий описан для будущей проверки; изменения в диаграмму и рендеринг на текущем этапе не выполнялись.

**Дополнительный случай постоянных ID:** на отдельной копии того же исходного примера пользователь просит после выхода из цикла, перед `РСЗ-03`, добавить «Зарегистрировать заключение», ответственный — «Согласующий», результат — «Заключение зарегистрировано». Новый шаг получает свободный `РСЗ-05`, прежние `РСЗ-01`–`РСЗ-04` сохраняются. Проверить, что новое действие находится только на пути к согласованию, а не внутри цикла доработки; перемещать его в конец схемы из-за номера `05` нельзя. Критерий — пять уникальных ID, сохранённый цикл и маршрут к согласованию через новый шаг. Этот случай также только описан.

## 8. Последующие этапы и критерий готовности

1. Зафиксированы переносимость между агентами и целевые среды Яндекс Wiki / HTML; при упаковке уточнить способ локального запуска и перечень систем для фактической проверки.
2. Детализирована методика трёх режимов; владелец выбрал постоянные ID. При подготовке скилла перенести правила заполнения, зависимости, уточнения и критерии готовности в его инструкции без дублирования справочника API.
3. Подготовлены четыре сложных маршрута; отображение подтверждено владельцем. Переносимые копии включены в пакет и техническую проверку экспортёра; новые публичные компоненты не потребовались.
4. После приёмки перехода окружения подготовлена версия `0.1.2-dev`: один Dockerfile задаёт PlantUML `1.2025.10` и лимит 4096, одна команда выдаёт исходники, SVG, HTML и `*_portable.puml` для Wiki. Профили и параметр `--target` удалены. Отложенный запрос о быстром предпросмотре не входит в этот этап. Технические проверки и команды — в контексте задачи.
5. Проверить учебные сценарии, затем по одному реальному случаю каждого режима, перенос комплекта и использование SVG в целевой среде. Согласованный объём проверки зафиксировать в задаче реализации; исторические проверки библиотеки не выдавать за проверки скилла.
6. Описать установку, версии, обновление и лицензию распространения.

Первая версия готова, когда пользователь в заявленной среде проходит все три сценария, получает согласованное содержание, воспроизводимый исходник и читаемый SVG, а агент корректно обрабатывает существенные пробелы и ошибки экспорта. При редактировании дополнительно сохраняются незатронутые правила и данные существующей схемы. Написанный `SKILL.md` сам по себе не означает готовность всего результата.
