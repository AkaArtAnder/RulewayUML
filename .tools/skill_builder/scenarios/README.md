# Образцы сложных маршрутов для будущего скилла

Это учебные образцы к [спецификации скилла](../specification.md). Владелец подтвердил корректное отображение всех схем после добавления полного набора параметров и сроков. Это подтверждение визуальной проверки пользователя, а не запуск тестов агентом или проверка кликов. Таблицы ниже задают ожидаемые маршруты.

Образцы используют существующие компоненты RulewayUML и стандартные конструкции [activity-диаграмм PlantUML](https://plantuml.com/activity-diagram-beta). Новых компонентов и обёрток переходов нет. Текущая базовая версия — `1.2025.10` из [Dockerfile](../../../.devcontainer/Dockerfile). При переходе окружения от 2026-09-23 повторную проверку отображения выполняет владелец; исходники образцов не меняются.

## Состав

| Задача | Исходник | Состав действий |
| --- | --- | --- |
| Получить два независимых результата перед продолжением | [parallel_results.puml](parallel_results.puml) | `РПВ-01`–`РПВ-03`, 3 действия |
| Дождаться внешнего ответа или заданного срока | [external_response.puml](external_response.puml) | `РОТ-01`–`РОТ-04`, 4 действия |
| Получить отсутствующее основание до решения | [missing_basis.puml](missing_basis.puml) | `РДО-01`–`РДО-06`, 6 действий |
| Продолжить основной процесс по результату дочернего | [subregulation_result.puml](subregulation_result.puml) | `РПМ-01`–`РПМ-05`, 5 действий |
| Передать результат из дочернего процесса | [subregulation_review.puml](subregulation_review.puml) | `РДП-01`–`РДП-04`, 4 действия |

Последние два файла составляют один образец. Все пять файлов самостоятельные; локальные подключения рассчитаны на их положение в репозитории. При переносе нужно сохранить доступ ко всему каталогу `components/` и изменить пути подключений. Дорожки в этих образцах опущены для компактности; ответственный указан в каждом действии. Это не устанавливает запрет на дорожки.

Учебные предпосылки явно перечислены для каждого образца. Агент выбирает подходящий маршрут по правилам конкретного регламента и не переносит предпосылки автоматически. Порядок действий определяется переходами; значения ID сохраняются при перемещении и вставке.

## Полнота заполнения параметров

В действиях `РПВ-01` и `РПМ-02` явно заполнены все семь параметров: ID, название, ответственный, результат, инструкция/чек-лист, срок/SLA и ссылка на подрегламент. Именованные аргументы позволяют увидеть назначение каждого значения. Другие действия показывают частичное заполнение необязательных полей; заполнять все семь в каждом шаге не требуется.

| Действие | Пример срока/SLA |
| --- | --- |
| `РПВ-01` — подготовить текст | 1 рабочий день после получения задания |
| `РПВ-02` — подготовить обложку | 2 рабочих дня после получения задания |
| `РОТ-02` — дождаться ответа | До получения ответа, но не позднее заранее установленного контрольного срока |
| `РПМ-02` — получить результат дочерней проверки | 1 рабочий день после получения материалов проверяющим; отдельно на каждый проход |
| `РДП-02` — проверить материалы | В пределах общего срока дочерней проверки, без нового отсчёта для этого шага |

Числовые сроки введены как учебные данные по запросу показать полный набор параметров. При применении к реальному регламенту агент использует сроки автора. SLA описывает норматив; сам по себе он не создаёт переход при просрочке. В образце внешнего ответа такой переход задан отдельно условием.

## 1. Параллельная подготовка результатов

**Учебное правило.** Задание и требования согласованы до запуска. Редактор и дизайнер могут работать независимо; подготовка обложки не требует результата редактора. Координатор начинает сборку только после готовности обоих результатов. Образец описывает подготовку комплекта, а не его публикацию.

`fork` разделяет работу, `end fork` объединяет её перед сборкой. Различия ролей недостаточно для выбора параллельности: основанием здесь служит независимость исходных данных и результатов.

| Ситуация | Ожидаемый маршрут |
| --- | --- |
| Первым готов текст | `РПВ-01` завершено; переход к `РПВ-03` ждёт результата `РПВ-02` |
| Первой готова обложка | `РПВ-02` завершено; переход к `РПВ-03` ждёт результата `РПВ-01` |
| Оба результата получены | `РПВ-03` → завершение с комплектом |

Сроки ветвей — 1 рабочий день для текста и 2 рабочих дня для обложки после получения задания. Действия при просрочке или невозможности подготовить результат в учебном правиле не заданы. Координатор ожидает оба результата; наступление срока не завершает ветвь автоматически. Если пользователь требует продолжать после первой готовой ветви, отменять другую ветвь или обрабатывать её неуспех, сначала уточнить эти правила: такая логика этим образцом не описана.

В `РПВ-01` ссылка на `https://example.org/regulations/text_preparation` демонстрирует заполнение параметра подрегламента. Это учебный адрес, содержимое внешнего регламента в комплект не входит. Для использования в своём процессе автор заменяет его своим адресом.

## 2. Внешний ответ и контрольный срок

**Учебное правило.** Вопрос, адресат и контрольный срок известны на старте; числового срока по умолчанию нет. Ответ, полученный не позднее срока, передаётся инициатору. Если ответа нет, инициатор получает уведомление и обработка этого запроса заканчивается. Поздние ответы находятся вне границ учебного процесса.

Ожидание оформлено действием `РОТ-02`: у него есть ответственная роль, наблюдаемый результат и предел ожидания. Условие использует зафиксированное наличие ответа и время его получения. Схема описывает работу координатора и не запускает таймер или автоматический мониторинг.

| Ситуация | Ожидаемый маршрут |
| --- | --- |
| Ответ получен до срока или точно в срок | `РОТ-01` → `РОТ-02` → «да» → `РОТ-03` → ответ передан |
| Наступил срок, ответа нет | `РОТ-01` → `РОТ-02` → «нет» → `РОТ-04` → завершено без ответа |

Завершение после уведомления — правило только этого примера. Для другого регламента агенту может потребоваться уточнить повторный запрос, эскалацию или продолжение без ответа. Отсутствие ответа не подменяется отрицательным ответом на сам запрос.

## 3. Отсутствующее основание решения

**Учебное правило.** Решение требует заключения. При его отсутствии координатор запрашивает документ и передаёт согласующему; решение принимается только после получения. Неполучение документа само по себе не является отказом в согласовании.

Вопрос «Заключение доступно?» опирается на проверку наличия в `РДО-01`. После обеих ветвей согласующий располагает заключением: его передаёт `РДО-02` либо получает и передаёт `РДО-05`. Вопрос о согласовании использует отдельный результат — решение `РДО-03`.

| Ситуация | Ожидаемый маршрут |
| --- | --- |
| Заключение уже есть | `РДО-01` → «да» → `РДО-02` → `РДО-03` |
| Заключения нет | `РДО-01` → «нет» → `РДО-05`; к `РДО-03` переходят после получения документа |
| Принято решение о согласовании | `РДО-03` → «да» → `РДО-04` → заявка согласована |
| Принято решение об отказе | `РДО-03` → «нет» → `РДО-06` → в согласовании отказано |

Два варианта получения заключения сочетаются с каждым из двух решений. Если заключение так и не получено, действие `РДО-05` остаётся незавершённым. Предельный срок и исход при невозможности получить документ здесь не определены; при потребности в такой обработке их нужно уточнить у автора.

`РДО-05` намеренно стоит перед `РДО-03` на одной из ветвей: новый шаг получает свободный ID, а уже существующие не перенумеровываются.

## 4. Результат дочернего регламента

**Учебное правило.** Основной процесс готовит материалы, организует проверку и получает её результат. Дочерний процесс либо выполняет проверку и возвращает заключение, либо сообщает, почему выполнить её невозможно. Заключение с замечаниями означает выполненную проверку и требует доработки материалов. Невозможность проверки в этом учебном процессе завершает подготовку без приёмки материалов после уведомления автора.

| Что передаётся между процессами | Содержание |
| --- | --- |
| Основной → дочерний | Комплект материалов и критерии проверки |
| Дочерний → основной, проверка выполнена | Статус «выполнена» и заключение с замечаниями либо явной отметкой об их отсутствии |
| Дочерний → основной, проверка не выполнена | Статус «не выполнена» и причина |

`РПМ-02` описывает организацию проверки и получение ответа координатором. Действия проверяющего раскрыты в отдельном файле. Ссылки служат навигации читателя; они не запускают дочерний процесс и не управляют возвратом. Завершение дочерней схемы само по себе не означает завершения основного регламента.

На каждый проход дочерней проверки задан общий учебный срок — 1 рабочий день после получения материалов проверяющим. Он включает оценку возможности, саму проверку и передачу результата либо причины невозможности. SLA в `РДП-02` напоминает об этом общем сроке, не добавляя отдельный день. При повторной передаче доработанных материалов отсчёт начинается заново; число повторов и общий срок всех доработок этим не ограничиваются. Просрочка сама по себе не означает статус «не выполнена»; отдельный маршрут при просрочке здесь не задан.

| Полученный результат | Ожидаемый маршрут в основном процессе |
| --- | --- |
| Проверка выполнена, замечания есть | `РПМ-02` → «да» → `РПМ-03` → цикл «да» → `РПМ-01` → повторная проверка |
| Проверка выполнена, замечаний нет | `РПМ-02` → «да» → `РПМ-03` → цикл «нет» → `РПМ-04` → материалы приняты |
| Проверка не выполнена | `РПМ-02` → «нет» → `РПМ-05` → завершено без проверки и приёмки |

На пути невозможности проверки заключение не требуется: этот путь завершается до условия о замечаниях. При повторе используется последнее заключение; повторное выполнение действий не создаёт новые ID. Число доработок не ограничено учебным правилом. Если пользователь задаёт предел, вместе с ним нужно определить дальнейший исход.

При экспорте оба SVG нужно разместить в одном каталоге с именами, соответствующими исходникам. В `subregulation_result.puml` задана учебная ссылка `subregulation_review.svg`, в дочернем файле — обратная `subregulation_result.svg`. Пока SVG не созданы, это только предусмотренные цели ссылок. В реальном регламенте адреса задаёт пользователь; доступность его ресурсов и права читателей скилл не проверяет.

## Как использовать при подготовке скилла

1. Сопоставить правила пользователя с предпосылками подходящего образца. Если меняется условие продолжения, сначала определить требуемый маршрут.
2. Применить нужный фрагмент в регламенте: сохранить API компонентов, заполнить данные предметной области, назначить новым действиям свободные ID. Не подменять существующие идентификаторы и ссылки.
3. Сверить основной путь, альтернативы и повтор с правилами регламента. Для параллельности отдельно проверить набор необходимых результатов; для дочернего процесса — каждый возвращаемый статус.
4. Использовать образцы при сборке скилла с учётом подтверждённого владельцем отображения. Проверки нового экспортёра выполнять в контейнере на переносимой копии; отдельно фиксировать технические результаты и фактическую проверку кликов. Приёмку пользователем не подменять утверждением об автоматических тестах.

Ход подготовки и ограничения текущего этапа записаны в [контексте задачи](../../../docs/tasks/2026_09_22_agent_skill.md). Эти образцы дополняют три сценария проверки поведения скилла, а не заменяют их.
