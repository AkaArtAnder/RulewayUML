# Инструкции для агентов — RulewayUML

## Контекст и порядок чтения

Перед изменениями прочитай [README.md](README.md), [docs/context.md](docs/context.md) и файлы, относящиеся к задаче. При работе с оформлением изучи [docs/ruleway_design/README.md](docs/ruleway_design/README.md); при изменении окружения — `.devcontainer/Dockerfile` и `.devcontainer/devcontainer.json`.

`docs/context.md` хранит продуктовый контекст, источники, принятые решения и открытые вопросы. Этот файл задаёт порядок работы. Явно различай реализованное, принятое решение и предложение; не выдавай планируемые каталоги, команды и компоненты за существующие.

При продолжении задачи прочитай её отдельный файл контекста из реестра задач ниже и продолжай с зафиксированного состояния.

## Продуктовые ориентиры

- Развиваем библиотеку переиспользуемых компонентов PlantUML для регламентов. Основное представление — диаграммы деятельности, а «компонент» означает элемент библиотеки, не отдельный тип UML-диаграммы.
- Самостоятельное приложение исключено действующим решением владельца проекта. Не добавляй UI, backend, базу данных, авторизацию или движок исполнения без новой задачи, меняющей объём продукта.
- Исходная заметка AFFiNE описывает более широкую идею. Переноси из неё требования к содержанию регламентов с учётом адаптации в `docs/context.md`, а не весь функционал приложения.
- Роли, сроки, контроль, метрики и чек-листы описываются на схеме. Их фактическое исполнение и автоматический учёт не являются функциями библиотеки.
- Приоритет — понятность действий, ответственности, входов, результатов и переходов. Декоративное оформление не должно ухудшать читаемость.

## Состояние и структура

В продолжение диагностики шрифтов исследована адаптация параметров схемы к семейству и размеру текста. Временные варианты с вычисляемой шириной/отступами успешно собраны на `1.2025.10`; пересчёт выполняется при генерации. Готовый SVG не перестраивает блоки и переходы при подстановке шрифта на Windows, поэтому прототип не заявлен исправлением текущего дефекта. Публичный стиль и API не менялись; результаты — в контексте диагностики ниже.

Диагностика от 2026-09-23: после резервной цепочки `DejaVu Sans, Arial, sans-serif` владелец подтвердил улучшение в Wiki на Windows 10, но сообщил о больших промежутках между словами. Измерено различие метрик при фиксированных координатах слов; вариант не принят как окончательный. Самостоятельный `docs/design/wiki_compatibility/external_response_font_fallback.puml` проверен на `1.2025.10` (синтаксис, SVG/PNG, режим предпросмотра, действующий Dev Container), сохранён для сравнения. Новый `docs/design/wiki_compatibility/wiki_font_inventory.puml` со штатной командой `listfonts` собран в Docker для определения шрифтов движка Wiki; его локальный вывод не подтверждает состав сервера Wiki. В штатном образе проекта Arial и Liberation Sans заменяются на DejaVu Sans. В самостоятельных проверочных файлах не повторяй маркеры начала/конца в комментариях: расширение VS Code распознаёт их как границы. Общий стиль, окружение и скилл не изменены. Продолжение — [контекст диагностики](docs/tasks/2026_09_23_wiki_windows_fonts.md); изменение локального экспортёра само по себе не исправляет блок, который рендерит Wiki.

Реорганизация разработки скилла в `.tools/skill_builder/` с единственным ZIP в `dist/` принята владельцем 2026-09-23. По решению от 2026-10-03 готовый ZIP включается в репозиторий, а сырые результаты тестов не хранятся: воспроизводимые задания и компактные отчёты находятся в `.tools/skill_builder/tests/`. Этап структуры завершён; кликабельность в Wiki и внешняя переносимость остаются дальнейшей работой.

Первый режим скилла проверен 2026-09-28 на реальном утверждённом регламенте рабочих совещаний/переписок и принят владельцем. Схема и отдельный фрагмент экспортированы на `1.2025.10`; диагностические пробелы признаны ожидаемым следствием недостатка сведений. 2026-10-03 агент дополнительно прогнал пять подготовленных учебных случаев всех трёх режимов и полный локальный технический контур: со скиллом 40/40 критериев, контроль 39/40 при одном запуске. Исходники скилла по итогам не менялись. Реальные пользовательские случаи разработки с нуля и редактирования, другая агентная система и кликабельность Wiki остаются дальнейшей работой; подробности — в задаче и отчёте скилла.

2026-09-23 владелец успешно проверил схемы после перехода на PlantUML `1.2025.10` и лимит 4096 и принял окружение. [Переход завершён](docs/tasks/2026_09_23_plantuml_baseline.md). Следующим поручением скилл приведён к тому же окружению без профилей; прежний запрос о быстром предпросмотре остаётся отложенным.

Образ `rulewayuml-dev:plantuml-1.2025.10` успешно пересобран из текущего Dockerfile без дополнительных аргументов. Версия и лимит подтверждены, схемы не проверялись. После пересборки действующего Dev Container CLI и предпросмотр используют эту же версию.

На 2026-09-22 есть общий стиль и четыре компонента: действие, условие, начало и завершение. Задачи всех четырёх компонентов завершены. В `examples/` восемь схем, включая два варианта основного процесса, дочернюю проверку, три примера условия и два примера границ; сохраняются шаблон результата, документация, фирменные материалы, Dev Container и проверки окружения/действия. По уточнению владельца действие уже завершено и внесено в библиотеку, текущих работ по нему нет; запись ожидания приёмки была устаревшей. Дополнительные проверки при фиксации завершения не запускались. CI и общей системы сборки пока нет. Перед работой проверяй актуальное дерево и `git status`.

Первый режим принят на одном реальном регламенте; пять учебных случаев всех режимов локально пройдены 2026-10-03. ## Соглашения для реализации

- Документацию, комментарии о предметной области и пояснения пользователю пиши по-русски. Имена файлов и публичных идентификаторов API делай понятными, на латинице; для файлов используй единый стиль `lower_snake_case`. Отображаемые идентификаторы действий — предметные данные: для них действует согласованный формат `РСТ-03` с кириллической `Р`. Тексты диаграмм должны поддерживать кириллицу и UTF-8.
- Предпочитай стандартные возможности PlantUML и небольшие подключаемые определения. Действие реализовано через `!include` и `!procedure`; не добавляй обёртки без необходимости.
- Отделяй переиспользуемые определения и настройки оформления от данных конкретного регламента. В подключаемых модулях не размещай случайный демонстрационный процесс; примеры должны быть отдельными самостоятельными диаграммами.
- Для публичных определений используй префикс `ruleway_`. API действия: `$ruleway_action($id, $name, $responsible, $result, $instruction = "", $sla = "", $subregulation = "")`; все аргументы — строки. По решению владельца от 2026-09-22 обязательны идентификатор, наименование, ответственный и результат. Инструкция/чек-лист, срок/SLA и ссылка на дочерний регламент используются независимо по необходимости; все три можно пропустить. Пустые необязательные поля скрываются. Сохраняй документированный порядок и имена.
- API условия, принятый 2026-09-22: `$ruleway_condition($question, $basis)` — функция, оба аргумента обязательные строки. Вопрос и основание задаются внутри стандартных `if` и `repeat while`; не вводи отдельный ID условия или обёртки переходов. Работа по проверке и ответственный остаются в предшествующем действии. Подписи исходов, существование основания и смысл маршрутов проверяет автор; функция отклоняет только пустые строки.
- API границ: `$ruleway_start_label($event, $inputs = "")` и `$ruleway_end_label($outcome, $result = "")` — функции с обязательным первым строковым аргументом. Сохраняй `start`, `stop` и `note right` явно в исходнике, размещай вызов внутри примечания сразу после маркера. Необязательные поля скрываются при `""`. Не добавляй ID границ, словарь событий/исходов или исход по умолчанию.
- Не скрывай логику процесса за избыточными обёртками. Компоненты должны сочетаться со стандартными конструкциями activity-диаграмм.
- По уточнению владельца от 2026-09-22 каждое действие в схемах регламентов и проверочных примерах компонента оформляй через `$ruleway_action(...)`. Обычные узлы `:Действие;` без обязательных полей недопустимы. Стандартные `if`, `repeat`, `fork`, дорожки и стрелки сохраняются. При добавлении действия актуализируй идентификаторы и проверку полного набора действий.
- Каждый новый публичный компонент сопровождай назначением, параметрами, минимальным рабочим примером и существенными ограничениями.
- По решению владельца от 2026-09-22 пользовательскую документацию веди в `docs/specification/`, описания компонентов — в `docs/specification/components/`. Оставляй там назначение, возможности, правила применения и примеры. Историю согласований, выводы этапов, измерения и результаты проверок фиксируй в `docs/context.md`, ТЗ и `docs/tasks/`; не добавляй их в пользовательские руководства.
- При изменении интерфейса уже используемого компонента обновляй все затронутые примеры и документацию; несовместимость указывай явно.
- Используй существующую палитру Ruleway как ориентир, проверяя читаемость. Не меняй логотипы и не переименовывай дизайн-ресурсы в рамках несвязанной задачи. Для SVG-знака используй принятые залитые контуры; PNG и обычные растровые спрайты не отображаются в проверенном способе вставки Wiki.
- Общие стили регламентов поддерживай в `components/style.puml`: DejaVu Sans, фон `#F5F8F7`, белые шаги, тёмно-синий текст, бирюзовые линии и мятные выделения.
