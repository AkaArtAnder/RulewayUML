# Инструкции для агентов — RulewayUML

## Контекст и порядок чтения

Перед изменениями прочитай [README.md](README.md), [docs/context.md](docs/context.md) и файлы, относящиеся к задаче. При работе с оформлением изучи [docs/ruleway_design/README.md](docs/ruleway_design/README.md); при изменении окружения — `.devcontainer/Dockerfile` и `.devcontainer/devcontainer.json`.

`docs/context.md` хранит продуктовый контекст, источники, принятые решения и открытые вопросы. Этот файл задаёт порядок работы. Явно различай реализованное, принятое решение и предложение; не выдавай планируемые каталоги, команды и компоненты за существующие.

При продолжении задачи прочитай её отдельный файл контекста из реестра задач ниже и продолжай с зафиксированного состояния.

## Продуктовые ориентиры

- Развиваем библиотеку переиспользуемых компонентов PlantUML для регламентов. Основное представление — диаграммы деятельности, а «компонент» означает элемент библиотеки, не отдельный тип UML-диаграммы.
- Самостоятельное приложение исключено действующим решением владельца проекта. Не добавляй UI, backend, базу данных, авторизацию или движок исполнения без новой задачи, меняющей объём продукта.
- Исходная заметка AFFiNE описывает более широкую идею. Переноси из неё требования к содержанию регламентов с учётом адаптации в `docs/context.md`, а не весь функционал приложения.
- Роли, сроки, контроль, метрики и чек-листы описываются на схеме. Их фактическое исполнение и автоматический учёт не являются функциями библиотеки.
- Приоритет — понятность действий, ответственности, входов, результатов и переходов. Декоративное оформление не должно ухудшать читаемость.

## Состояние и структура

На 2026-09-17 в проекте есть документация, фирменные материалы и конфигурация Dev Container. Реализации библиотеки, `.puml`-примеров, тестов, CI и сборочных сценариев пока нет. Перед работой проверяй актуальное дерево и `git status`: этот снимок состояния необходимо обновлять по мере развития проекта.

- `docs/context.md` — основной контекст проекта.
- `docs/tasks/` — каталог контекстов отдельных задач: постановка, решения, ход работы, проверки и результат; создаётся при появлении задач. После очистки завершённых задач файлов контекста в нём нет.
- `docs/ruleway_design/` — существующие ресурсы бренда; сохраняй их при работе над библиотекой.
- `.devcontainer/` — окружение Java 17 и PlantUML `1.2026.5`; версия берётся из `ARG PLANTUML_VERSION` в Dockerfile.
- `lib/`, `examples/`, `tests/` — предложенные в контексте каталоги, пока не созданные. Добавляй их по мере появления реальных файлов.

Наличие Maven в контейнере не требует создавать Maven-проект. Не вводи дополнительные языки, генераторы или инфраструктуру без необходимости для текущей задачи.

## Соглашения для реализации

- Документацию, комментарии о предметной области и пояснения пользователю пиши по-русски. Имена файлов и публичных идентификаторов делай понятными, на латинице; для файлов используй единый стиль `lower_snake_case`. Тексты диаграмм должны поддерживать кириллицу и UTF-8.
- Предпочитай стандартные возможности PlantUML и небольшие подключаемые определения. Рабочее направление — `!include`, `!procedure` и `!function`; точный API формируется с первой реализацией.
- Отделяй переиспользуемые определения и настройки оформления от данных конкретного регламента. В подключаемых модулях не размещай случайный демонстрационный процесс; примеры должны быть отдельными самостоятельными диаграммами.
- Для публичных определений используй согласованный префикс проекта, чтобы избежать конфликтов имён при подключении. Выбранный префикс и правила вызова документируй при введении API.
- Не скрывай логику процесса за избыточными обёртками. Компоненты должны сочетаться со стандартными конструкциями activity-диаграмм.
- Каждый новый публичный компонент сопровождай назначением, параметрами, минимальным рабочим примером и существенными ограничениями.
- При изменении интерфейса уже используемого компонента обновляй все затронутые примеры и документацию; несовместимость указывай явно.
- Используй существующую палитру Ruleway как ориентир, проверяя читаемость. Не меняй логотипы и не переименовывай дизайн-ресурсы в рамках несвязанной задачи.
- Сохраняй фирменное оформление README: локальные SVG-логотипы для светлой и тёмной темы через `<picture>`, слоган и навигацию. Используй Markdown и простые HTML-элементы без зависимости от пользовательского CSS; при визуальных изменениях проверяй обе темы и узкий экран, включая ширину таблиц. Указывай, если проверялся только локальный предпросмотр.
- README адресован пользователю, который хочет взять практики и компоненты для своих регламентов. Держи его кратким: назначение, полезные практики, доступные компоненты и пользовательские примеры по мере их появления. Планируемые возможности обозначай явно. Подробности разработки, окружения, продуктовой аналитики и ведения задач размещай в `AGENTS.md` и `docs/context.md`; не превращай README в инструкцию по разработке и каталог внутренних документов.
- Первые примеры должны воспроизводиться с локальным подключением библиотеки. Если добавляешь внешние зависимости, фиксируй их версии и способ получения.

## Проверка изменений

Для правок только документации проверь фактическую структуру репозитория, корректность ссылок и непротиворечивость `README.md`, `docs/context.md` и `AGENTS.md`. Сверяй версию PlantUML с Dockerfile. Не запускай сборку окружения только ради правки текста.

После появления компонентов и примеров:

1. Используй версию PlantUML из окружения проекта. В успешно собранном Dev Container доступны `plantuml -version` и `plantuml -help`; оболочка запускает `/opt/plantuml/plantuml.jar`. Если команда отсутствует, сообщи об этом ограничении, а не о прохождении проверки.
2. Проверь синтаксис и отрендери затронутые самостоятельные диаграммы. Подключаемые определения проверяй через использующие их примеры. Флаги запуска сверяй со справкой установленной версии; рабочие команды зафиксируй вместе с первым примером.
3. Просмотри результат: подписи не обрезаны, кириллица читается, роли и ветвления понятны, блоки не переполнены. При изменении общих стилей или интерфейса проверь все зависимые примеры.
4. Для нового поведения выбирай содержательные случаи: длинный текст, необязательные поля, несколько ролей, условия, ссылки и подрегламент — по применимости. Не создавай тесты, лишь повторяющие реализацию.
5. Отдельно проверяй ссылки и переходы в том формате и среде просмотра, для которых заявляется поддержка. Успешный рендеринг не подтверждает работу навигации.

Справочники: [activity-диаграммы](https://plantuml.com/ru/activity-diagram-beta), [препроцессор](https://plantuml.com/preprocessing), [командная строка](https://plantuml.com/command-line). Документация сайта может описывать более новую версию, чем закреплена в проекте.

Не сохраняй временные результаты рендеринга в исходниках. При появлении постоянного каталога сборки добавь для него точечное правило в `.gitignore`; не исключай все SVG/PNG, поскольку в репозитории есть исходные материалы бренда в этих форматах.

## Рабочий процесс и актуализация контекста

- Сначала проверь рабочее дерево. Сохраняй пользовательские изменения, в том числе ещё не отслеживаемые Git файлы; не подменяй их своей версией без связи с задачей.
- Делай изменения в пределах задачи. Не создавай каркас приложения, фиктивный API, пустые каталоги или CI ради заполнения структуры.
- Обновляй `docs/context.md`, когда меняются продуктовые границы, принятое устройство библиотеки, способ использования, окружение или текущая стадия. Для значимых решений фиксируй дату, основание и последствия; подробные решения при необходимости выноси в отдельные документы с ссылками из контекста.
- Синхронизируй README с фактическим состоянием: инструкция должна вести к существующему и проверяемому результату.
- В итоговом сообщении укажи, что изменено, какие проверки выполнены и что осталось непроверенным. Не приписывай проекту проведённые исследования, поддержку форматов или автоматизацию, которых нет.

### Контекст каждой задачи

Правило принято владельцем проекта 2026-09-17 и обязательно для каждой новой задачи, включая изменения документации.

1. **В начале задачи**, после чтения общего контекста и до основных изменений, создай отдельный файл `docs/tasks/YYYY_MM_DD_short_task_name.md`. Используй дату начала и краткое название на латинице в стиле `lower_snake_case`; при совпадении имён добавь числовой суффикс. Продолжение и уточнения одной задачи веди в существующем файле.
2. **Сразу добавь ссылку** на созданный файл в реестры задач в `docs/context.md` и корневом `AGENTS.md`. Укажи дату, название и статус. В самом файле задачи добавь обратные ссылки на оба общих документа.
3. **Зафиксируй исходный контекст:** цель, основание или запрос пользователя, границы, ограничения, исходное состояние и оставшиеся действия. Укажи дату начала и статус `в работе`.
4. **По ходу работы дополняй этот же файл** после значимых изменений: принятые решения и их основания, затронутые файлы, результаты проверок, выявленные ограничения и следующие шаги. При паузе зафиксируй точку продолжения; при блокировке — причину. Поддерживай краткую фактическую запись, достаточную для продолжения работы в другой сессии.
5. **После завершения задачи** запиши итог, выполненные проверки, ограничения и дату завершения, установи статус `завершена`. Если остаётся обязательная работа, оставь соответствующий незавершённый статус и перечисли её. Синхронизируй статус в обоих реестрах.
6. **Перед итоговым ответом обнови `docs/context.md` и `AGENTS.md` актуальными доработками:** перенеси в общий контекст новое состояние проекта, принятые решения и открытые вопросы, а в инструкции — изменившуюся структуру, команды и правила работы. В реестрах кратко укажи результат задачи. Если продукт или реализация не изменились, отражай фактическое изменение документации без выдуманных доработок. Подробную историю сохраняй в файле задачи. По явному запросу пользователя удаляй завершённые файлы и ссылки на них из обоих реестров, предварительно убедившись, что актуальные решения перенесены в общие документы.
